# Lesson 30: Math expressions, bytebeat, and JIT C++

{% include lesson_meta.html %}

> **Before this lesson** finish [Lesson 29]({{ site.baseurl }}/learn/29-javascript-processes.html), because it assumes the script editor and its compile loop are familiar.
>
> **You will need** a device with a few parameters, and speakers or headphones.
>
> **You will build** three small computations, which are a mapping written as a formula, an array generated by expression, and a sound produced by arithmetic.

## Why this matters

Lesson 29 introduced JavaScript as the general-purpose route, whereas this lesson covers the specialised routes beside it, which are preferable because a smaller tool is easier to read, faster to run, and harder to get wrong. A relationship which is a formula should therefore be written as a formula, since `sqrt(x) * 0.8 + 0.1` is clearer than a drawn curve that approximates it or twelve lines of script that compute it.

The lesson also introduces compiled code inside a document, which sounds heavier than it is, since a just-in-time (JIT) compiled expression runs at full speed on the machine that opens the document, which matters when a computation happens for every audio sample or every pixel. In other words, the question this lesson keeps returning to is how often a computation runs, because the rate decides which tool it needs.

## Concepts

### Math expressions

Math expression processes evaluate a formula that you write directly on the process. The smallest of them, usually called a micromap, multiplies and offsets in one step, which is the most common conditioning operation in the course and appeared in Lesson 28, while the fuller expression objects accept arbitrary formulas with variables, functions, and conditionals.

### Array generators and mappers

Array generators and mappers are expression objects that produce or transform whole arrays. An array generator returning `[cos(2*pi*i/n), sin(2*pi*i/n)]` lays out points on a circle, which is the speaker layout of Lesson 22 and the geometry of Lesson 27 in one line, while an array mapper applies a formula to every element.

### Bytebeat

Bytebeat produces audio from a formula evaluated over a sample counter. It is a small and strange corner of computer music, in which a handful of arithmetic operations on an integer produce rhythmic and harmonic material, and its practical value here is pedagogical, since it makes the relationship between arithmetic and sound immediate.

### JIT compiled C++

A just-in-time compiled C++ process compiles its script when you press compile and then runs it natively. It is the route when a computation must happen at a high rate, for every sample or every element of a large array, and the expression objects are not enough. Furthermore, it is the route to an existing algorithm you have in C++, which can run inside the document without becoming a plug-in.

### Cost and rate

The cost of an expression depends on the rate at which it runs. Once per tick it is free in any practical sense. In contrast, for every audio sample it is a different proposition, and for every pixel it belongs in a shader, which is the idea the section on rates below develops.

The figure shows Lesson 04's document with one object inserted. The automation no longer writes to `lesson:/level`; it writes into an `Expression Value Filter`, which applies `sqrt(x) * 0.8 + 0.1` and writes the result to the parameter. The device explorer on the left shows that result, `0.893403`, where the fade ends, which puts the whole lesson on one screen, because the relationship is written and sits where a mapping curve would sit.

Moreover, the formula lives on the process itself, in a field you type into, whereas only the heavier routes, the JavaScript of Lesson 29 and the C++ below, open an editor window.

{: .note }
> **Four expression objects exist in 3.8.2, and their formulas share one set of variables.** Filtering the process library for `expression` returns `Expression Value Filter` under `Control > Mappings` and `Expression Value Generator` under `Control > Generators`, together with `Expression Audio Filter` and `Expression Audio Generator` under `Audio > Utilities`; a filter takes an input, whereas a generator does not. `Micromap` sits beside the first, under `Control > Mappings`. The variables a formula can use are `a`, `b`, and `c`, which are the three parameters carried on the object itself and therefore automatable, `t` in samples, `dt` for the delta, `pos` for the position in the parent interval, and `x` for the incoming value, and the engine underneath is ExprTK.

1. **Start with the smallest object, a micromap inserted between a sensor value and a destination.** Set a multiplier and an offset, and you have the conditioning stage of Lesson 13 in a single process.
2. **Write a real formula by replacing the micromap with a full expression object.** Give it a relationship that is not a straight line, a square root or a squared curve, and compare the feel with the mapping curve you drew in Lesson 13. Dropping the object onto a selected process cables it in and takes over the destination address, as the figure shows.
3. **Note which of the two is more readable, and form an opinion.** For a collaborator a drawn curve is often clearer, whereas for you a formula is exact and reproducible, and both positions are defensible.
4. **Generate an array of eight positions on a circle with an array generator**, and view them with a point view, which gives you a parametric layout, the recommendation of Lesson 22 implemented.
5. **Automate the count or the radius so that the layout changes over the piece**, which no hand-placed set of points can do.
6. **Map the array element-wise by adding an array mapper that scales every element**, and confirm the result with the point view.
7. **Make sound from arithmetic by adding a bytebeat process.** Listen to the default, then change one constant, which is the fastest available demonstration that sound is arithmetic.
8. **Write a C++ process of your own, however small the computation.** Add a just-in-time C++ process and implement a soft clipper, a running average, or a threshold with hysteresis, then compile it and cable it in.
9. **Break it by introducing a compile error**, and confirm that the running document is unaffected while the error appears in the editor's pane.

   {: .note }
   > **The routes that open an editor share one compile loop.** The C++ process, like the JavaScript of Lesson 29, uses the script editor and its compile action, `Ctrl+Enter`, and refuses invalid code while the previous version keeps running, as Lesson 26's shaders did, so learning that loop once serves every editor-based route in Module J.

10. **Compare rates by putting the same computation in an expression object and in the C++ process**, both at control rate, and confirm that both are fine. Then consider what would change once per audio sample, which is the judgement the lesson is teaching.

## Choosing among five routes

By the end of Module J you will have five ways to write behaviour, namely the utility processes of Lesson 14, which need no code, and the four scripting routes of this module: JavaScript in Lesson 29, expressions and JIT C++ here, Faust in Lesson 31, and Pure Data in Lesson 32.

**A utility process is the first choice whenever one exists**, because it is visible in the score, needs no code, and has no compile step.

**A math expression is the choice when the behaviour is a formula over a few values**, since it is small, exact, and readable by anyone who reads arithmetic.

**JavaScript is the choice when the behaviour needs state, conditionals, or generation at control rate**, and it is the most flexible of the five, the least fast, and the easiest to write.

**Faust, in [Lesson 31]({{ site.baseurl }}/learn/31-faust.html), is the choice for whatever processes audio signals**, because it is designed for that purpose, compiles for the machine that runs it, and brings a large library.

**Just-in-time C++ is the choice when none of the others fits**, which means an existing algorithm, an unusual data structure, or a computation whose rate makes the others too slow.

A useful heuristic is to try them in that order and to stop at the first that works, although the pull usually runs the other way, because the more capable tools are more interesting. However, the resulting document is harder for anyone else to read.

## Rates, and why they decide the tool

Every computation happens at a rate, and the rate determines which tool is appropriate, which is the single most useful idea in this lesson.

**Per-tick computation happens at the control rate, perhaps a few hundred times a second.** Any tool works at this rate, an expression, a script, or a chain of utility objects, so the choice should follow readability alone.

**Per-sample computation happens tens of thousands of times a second.** In contrast, a control-rate tool used at this rate is either impossible or badly aliased, which makes this Faust's territory, or compiled C++'s.

**Per-pixel computation happens potentially millions of times per frame.** It belongs in a shader, as Lesson 26 described, and none of the tools in this lesson is the right answer for it.

**Per-element computation over a large array falls between the second and the third.** The array-aware expression objects handle moderate sizes, whereas a compute shader handles large ones.

Asking how often a computation runs before asking what to write it in makes the choice almost automatic, and it explains why the same formula belongs in different places depending on where you need it.

## Common mistakes

- **A script where a micromap would do** is the most common over-engineering in this software.
- **A drawn curve approximating a formula you already know** hides a relationship that could be exact; if you can write it, write it.
- **Hand-placing points that an expression could generate** produces a layout that cannot be automated or reused.
- **Per-sample work in a control-rate tool** will be either slow or aliased, so it belongs in Faust or C++.
- **Per-pixel work anywhere but a shader** costs more than it should; Lesson 26 is the right place.
- **Forgetting to compile** is the failure every scripting route shares, since edited code has no effect until it is applied.
- **Reaching for C++ first** ignores that the compile step and the debugging cost are real, which is why it is the last resort.

## Exercise

Implement the same relationship three ways, as a drawn mapping curve, as a written expression, and as a just-in-time C++ process, then drive the same destination with each and confirm that they agree. Then write two sentences that say which version you would ship in a document a collaborator will edit and which in an installation that must run for a month.

**Success criterion:** all three produce the same output for the same input, and your two sentences give different answers with reasons. Additionally, generate an eight-point circular layout by expression and automate its radius, since any hand-placed point has missed what the array generators are for.
